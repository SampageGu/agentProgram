# MiniCode M0–M5.2 统一验收指南

本文用于亲自判断 MiniCode 从 M0 到 M5.2 是否真正通过。命令正常退出不等于功能通过；只有对应阶段的功能证据全部出现，才可以记录为 PASS。

## 0. 验收前准备

### 0.1 配置 DeepSeek

在项目根目录打开 PowerShell：

```powershell
cd D:\000Study\agentProgram
Copy-Item .env.example .env   # 已存在 .env 时不要覆盖
notepad .env
```

至少填写：

```dotenv
DEEPSEEK_API_KEY=你的真实Key
MINICODE_BASE_URL=https://api.deepseek.com
MINICODE_MODEL=deepseek-v4-flash
```

API Key 只能放在 `.env`，不要写进 Prompt、代码、截图或验收记录。

### 0.2 先跑离线基线

```powershell
.\start.cmd test
```

当前版本 `0.9.0` 的正确结果是：

```text
Ran 46 tests
OK
```

这一步不会调用 DeepSeek，不消耗 Token。若不是 `46 tests + OK`，先停止人工验收。

### 0.3 验收范围与成本

- `test`、`security`、`status`、`replay` 不调用模型；
- `demo`、`demo2`、`webdemo` 中提交任务、`resume`、`eval3` 会调用 DeepSeek；
- M5.2 已默认启用，CodingAgent 可能额外创建 Explore child，因此一次任务可能产生父、子两层模型调用；
- `webdemo` 使用一次性 workspace，适合安全验收；普通 `web` 直接操作项目根目录，不建议用于第一次修改实验。

## 1. M0：只读仓库分析

运行真实只读分析：

```powershell
.\start.cmd ask "M0 提供了哪些只读工具？请引用源码路径和行号"
```

必须看到：

1. 至少调用一次 `list_files`、`search_code` 或 `read_file`；
2. 回答引用真实的相对路径和行号；
3. 终端为流式输出，Trace 中存在 `run_started`、工具事件和 `run_completed`；
4. Agent 不能读取 `.env`、`.git`、`.mini-code` 或 workspace 外文件；
5. `git diff` 不包含 Agent 对仓库的修改。

复制 Run ID 后检查 Trace：

```powershell
.\start.cmd trace <run_id>
```

可选的 5 题真实评测：

```powershell
.\start.cmd eval
```

至少 4/5 通过、没有运行时错误、报告不含 API Key，才算 M0 PASS。

## 2. M0.1：终端连续对话

```powershell
.\start.cmd
```

在同一终端依次输入：

```text
请找到 Web 服务入口，并引用路径和行号
刚才那个入口如何限制监听地址？
/history
/clear
/exit
```

必须看到：

1. 第二问能理解“刚才那个入口”，说明进程内保留上下文；
2. `/history` 能显示本轮历史；
3. `/clear` 后旧上下文被清除；
4. 每轮都有独立 Run ID 和 Trace；
5. Markdown 星号不会以 `\*\*` 的形式污染终端输出。

终端聊天历史只在当前进程内；跨进程持久化属于 Coding Run 和 Web Conversation，不是 M0.1 的验收范围。

## 3. M1：修改、测试与完成协议

### 3.1 启动

```powershell
.\start.cmd demo
```

脚本会创建一次性除零 Bug 仓库，不会修改 MiniCode 源码。保存终端输出中的：

- `Disposable demo workspace`；
- Parent Run ID；
- 如果发生委派，还要保存 Child Run ID。

### 3.2 必须看到的证据

1. Agent 使用 `list_files`、`search_code` 或 `read_file` 检查真实代码；
2. 建立多步骤计划，并且同时最多只有一个 `in_progress`；
3. 使用 `apply_patch` 真正修改 `calculator.py`，不能只在回答里描述代码；
4. 至少执行一次 `run_tests`，最终测试通过；
5. 执行 `git_diff`，Diff 中只包含任务相关改动；
6. `finish_task` 成功，最终 Run 状态为 `completed`；
7. 最终回答包含修改文件、测试证据和剩余风险；
8. 如果调用 Explore child，父 Agent 必须在 Patch 前重新读取至少一个 child 引用的文件。

### 3.3 复核命令

```powershell
.\start.cmd status <parent_run_id> "<Disposable demo workspace>"
.\start.cmd replay <parent_run_id> "<Disposable demo workspace>"
```

如果有 Child Run ID，可查看独立 Trace：

```powershell
.\start.cmd trace <child_run_id> "<Disposable demo workspace>"
```

### 3.4 PASS / FAIL

M1 PASS：上述 8 项全部满足，或者未触发 Subagent 时前 7 项全部满足。

以下任意一项出现即为本次 FAIL：

- Agent 声称修复，但文件没有变化；
- 测试通过，但没有 Diff 或 `finish_task`；
- Patch 后没有重新运行测试；
- 最终状态为 `failed`、`budget_exhausted` 或 `cancelled`；
- 修改了与任务无关的文件。

模型偶发失败可以重跑，但必须保留失败 Trace，不能只记录最好的一次。

## 4. M2：上下文压缩、Checkpoint 与恢复

### 4.1 创建可恢复任务

```powershell
.\start.cmd demo2
```

该 Demo 会使用较小的上下文和步骤预算，目的是产生一个可恢复状态。保存 Demo workspace 和 Run ID。

### 4.2 检查暂停状态

```powershell
.\start.cmd status <run_id> "<Demo workspace>"
.\start.cmd replay <run_id> "<Demo workspace>"
```

第一次运行应为 `budget_exhausted`，而不是伪装成 `completed`。同时检查：

```text
<Demo workspace>\.mini-code\runs\<run_id>\checkpoints\
```

目录内应存在 JSON checkpoint。

### 4.3 恢复

```powershell
.\start.cmd resume <run_id> "<Demo workspace>"
```

恢复成功必须满足：

1. 使用原 Run ID，不创建一个冒充恢复的新父 Run；
2. 从 checkpoint 后续步骤继续；
3. 已成功执行的 Patch 不重复应用；
4. 计划、修改文件、工具状态和 Subagent 复核状态仍然存在；
5. 最终重新测试并通过完成协议；
6. Replay 中能看到实际发生的 `checkpoint_saved`、`run_resumed`，触发压缩时还能看到 `context_compacted`。

只有发生过的事件才要求出现；如果本次上下文没有达到压缩阈值，不应伪造 `context_compacted`。

### 4.4 工作区冲突保护

重新创建一个 `demo2`。暂停后手动修改该 Demo workspace 的 `calculator.py`，再执行：

```powershell
.\start.cmd resume <run_id> "<Demo workspace>"
```

正确结果是报告 `Resume conflict`、退出码为 3，并且 Agent 不继续 Patch。请用新的 Demo 副本测试，不要破坏准备正常恢复的唯一副本。

### 4.5 PASS / FAIL

- 正常恢复链路和冲突保护都符合预期：M2 PASS；
- 只保存文件但无法恢复工具/计划状态：FAIL；
- workspace 已变化仍继续 Patch：FAIL；
- resume 从头重复修改：FAIL。

## 5. M3：安全、Replay 与量化评测

### 5.1 安全策略离线验收

```powershell
.\start.cmd security
```

必须显示：

```text
15/15 blocked
```

并生成 `.mini-code/security/audit-*.json`。这只说明当前 15 个版本化探针全部被策略层阻断，不代表具有操作系统级沙箱。

### 5.2 Provider 故障恢复

只对可信测试仓库运行：

```powershell
.\.venv\Scripts\python.exe run_mini_code.py run `
  "修复 Bug，运行测试并查看 Diff" `
  --workspace D:\path\to\test-repo --env-file .env --fail-model-call 2
```

首次运行应明确出现 injected failure，并保留 Run ID 或 checkpoint。随后执行：

```powershell
.\start.cmd resume <run_id> "D:\path\to\test-repo"
.\start.cmd replay <run_id> "D:\path\to\test-repo"
```

Replay 必须同时反映失败、恢复和最终验证，不能把失败阶段隐藏掉。

### 5.3 小规模真实评测

先运行一题确认 Key、模型和评分链路：

```powershell
.\start.cmd eval3 1
```

通过标准：程序不崩溃，生成 `.mini-code/evals/m3-*/report.json`，报告包含：

- 模型、代码版本、Prompt 版本和日期；
- Task Success Rate、Public Test Pass Rate、Regression Rate；
- Unrelated Change Rate、平均步骤、P50/P95；
- Token 与成本字段；未配置价格快照时成本允许为 `null`。

### 5.4 完整 20 题评测（可选但推荐用于简历）

```powershell
.\start.cmd eval3 20
```

这一步会产生较多模型调用。建议项目投递底线是：报告完整、程序无崩溃、Task Success Rate 不低于 60%，且失败题保留 Trace 与如实分析。

### 5.5 PASS / FAIL

- 安全探针、故障恢复、Replay 和至少一题真实评测均通过：M3 基础 PASS；
- 完成 20 题并保存完整指标：M3 项目展示 PASS；
- 只展示成功任务、不保留失败样例：FAIL；
- 把 `15/15 blocked` 描述成“绝对安全”：验收表述 FAIL。

## 6. M4：本地 Web 控制面基础能力

### 6.1 安全启动

```powershell
.\start.cmd webdemo
```

终端会输出一次性 workspace，并启动：

```text
http://127.0.0.1:8765
```

浏览器必须通过 `127.0.0.1` 访问。不要将服务改为 `0.0.0.0` 或暴露到公网。

### 6.2 提交第一轮任务

输入：

```text
修复 calculator.py 中除数为零时崩溃的问题，使 safe_divide 返回 None；检查实现和测试，完成修改、测试与 Diff 验证。
```

### 6.3 M4 基础证据

1. 提交后创建 Parent Run，并开始 SSE 实时更新；
2. 不刷新即可看到模型输出、工具执行、计划、测试和 checkpoint；
3. 右侧“运行详情”能展开计划、验证证据、Session Diff 和事件时间线；
4. 计划状态正确，最多一个步骤为 `in_progress`；
5. 修改文件、测试结果、步骤、Token（Provider 返回 usage 时）和 checkpoint 能更新；
6. 最终状态为 `completed`，测试通过，完成协议成功；
7. 页面刷新后仍能恢复已确认的 Run、事件、计划和 Diff；
8. 服务只监听本机，浏览器无法传入或切换服务器 workspace。

### 6.4 取消与 CLI 恢复

新建一个对话，提交后尽快点击停止按钮。模型 HTTP 请求或测试子进程不会被强杀；系统应在安全边界进入 `cancelled` 并保存 checkpoint。

按页面或 Trace 中的 Parent Run ID，在停止 Web 服务后执行：

```powershell
.\start.cmd status <run_id> "<Disposable M4 workspace>"
.\start.cmd resume <run_id> "<Disposable M4 workspace>"
```

能够继续完成，则取消/恢复链路通过。

### 6.5 PASS / FAIL

- 正常 Run、刷新恢复、停止与 CLI resume 全部通过：M4 PASS；
- 页面只显示最终答案，没有 SSE 过程：FAIL；
- 刷新后事件丢失或重复：FAIL；
- 取消后没有 checkpoint：FAIL；
- 浏览器可指定任意本机目录：安全验收 FAIL。

## 7. M4.1：ChatGPT 式多轮对话与 Subagent 卡片

M4.1 验收必须在 M4 第一轮任务通过后继续进行，不需要重启 `webdemo`。

### 7.1 页面结构

必须同时看到：

1. 左侧：新建对话按钮和持久化会话历史；
2. 中央：用户消息、Agent 回答、底部固定输入框；
3. 右侧：可开关的 Run Inspector；
4. 运行中：发送按钮切换为停止按钮；
5. 工具调用：以可展开卡片出现，而不是把整段 JSON 混入回答。

### 7.2 连续追问

第一轮完成后，在同一会话输入：

```text
请再补一个除数为 0.0 的边界测试，不要重复已有修改；运行测试并重新检查 Diff。
```

成功标准：

1. 同一会话新增第二组“用户消息 + Agent 回答”；
2. 第二轮创建新的 Run ID，但仍使用同一个 Demo workspace；
3. 第二轮能看到第一轮修改后的真实文件状态；
4. 不重复应用第一轮 Patch；
5. 第二轮仍然完成计划、测试、Diff 和完成协议；
6. 左侧会话条目仍只有一个，但轮数增加。

当前实现采用“同一 workspace + 最近任务摘要 + 每轮独立 Run”，不是把全部历史工具输出无限传给模型。这是预期设计，不是上下文丢失。

### 7.3 刷新与服务重启恢复

1. 浏览器刷新，确认两轮消息、工具卡片和右侧证据仍在；
2. 按 `Ctrl+C` 停止服务；
3. 使用同一 Demo workspace 重新启动：

```powershell
.\.venv\Scripts\python.exe run_mini_code.py web `
  --workspace "<Disposable M4 workspace>" --env-file .env
```

4. 再次打开 `http://127.0.0.1:8765`，确认原会话仍存在；
5. 会话历史来自 `.mini-code/state.db`，不应依赖浏览器 `localStorage`。

`webdemo` 每次启动都会创建新的 Demo workspace，因此直接再次运行 `webdemo` 不会显示上一次 Demo 的会话，这属于预期行为。

### 7.4 Explore Subagent 卡片

M5.2 默认允许父 Agent 委派 Explore，但模型可能判断简单任务无需再次委派。若第一轮产生委派，必须看到：

1. 回答区域出现可展开的 `Explore Subagent · <child_run_id>` 卡片；
2. 卡片展示 child 的成功或失败状态以及结构化报告摘要；
3. 右侧 Subagent 数量大于 0；
4. 父 Trace 中存在 `subagent_delegated` 和 `subagent_result` 或 `subagent_failed`；
5. 成功 child 的证据在 Patch 前被父 Agent 重新读取。

如果本次没有发生委派，不能据此判定卡片功能失败；应改用更需要探索的任务重新验收，例如：

```text
先委派 Explore Subagent 定位 safe_divide 的实现、测试和潜在边界风险；父 Agent 复核证据后补充一个有价值的测试并完成验证。
```

### 7.5 多会话隔离

点击“新建对话”，发送一个不同任务。必须满足：

- 左侧出现第二个会话；
- 两个会话可以切换，消息不会串到一起；
- 同一个固定 workspace 同时最多运行一个任务；
- 前一个会话已经产生的代码修改仍属于该 workspace，因此新会话能观察到它们。

### 7.6 PASS / FAIL

M4.1 PASS 必须满足：页面结构、连续追问、刷新恢复、多会话切换全部通过；并且至少使用一次真实委派任务确认 Subagent 卡片。

以下任意一项出现即为 FAIL：

- 第二轮覆盖第一轮消息；
- 第二轮复用了同一 Run ID；
- 刷新后会话消失；
- 工具 JSON 直接污染正常回答；
- Explore 已成功委派但页面没有 child 卡片；
- 两个会话消息串线；
- 同一 workspace 同时启动两个 Coding Run。

## 8. M4.2：意图路由与对话/编码双模式

启动 `webdemo` 后，在输入框上方保持“自动”模式，依次完成以下三轮；可以分别新建对话，避免前一轮 workspace 修改影响观察。

### 8.1 普通对话：零工具

输入：

```text
你好
```

成功标准：显示 `自动 → 对话`；直接流式回复；本轮没有任何工具或 Subagent 卡片，也不出现仓库扫描结果。

### 8.2 仓库问答：只读工具

输入：

```text
项目入口在哪里？请引用文件证据。
```

成功标准：显示 `自动 → 只读问答`；只允许出现 `list_files`、`search_code`、`read_file`；不得出现计划、Patch、测试、命令或 Subagent。

### 8.3 编码任务：完整工具链

输入：

```text
修复 calculator.py 的除零问题，补充测试并检查 Diff。
```

成功标准：显示 `自动 → 编码任务`；可以计划、委派、Patch、测试和检查 Diff，并满足 M1/M5.2 的完成门禁。

### 8.4 手动模式、持久化与显示

1. 选择“对话”，输入一个包含“修改代码”字样的讨论问题，本轮仍应零工具；
2. 新建对话后模式应恢复为“自动”；
3. 刷新页面，历史轮次的请求模式和实际意图徽标仍然存在；
4. 有工具调用的任务中，最终回答只能显示最后一次模型输出，不能拼接“我先调用工具”等中间模型文本；
5. 选择“编码”会强制进入完整 CodingAgent，因此不要仅为试按钮而对真实仓库发送问候，建议只在 `webdemo` 验收。

M4.2 PASS：三类自动路由、手动对话覆盖、刷新持久化和最终答案显示全部通过。问候仍扫描仓库、只读问题获得写工具、或明确修改任务未进入编码流程，任一情况均为 FAIL。

## 9. M5.1：独立 Explore Subagent

### 9.1 启动

```powershell
.\start.cmd explore "定位 M4 Web 服务入口、HTTP 路由和安全边界，请给出路径与行号证据"
```

### 9.2 必须看到的证据

1. 显示 Explore Subagent 启动，并产生独立 Child Run ID；
2. child 只有 `list_files`、`search_code`、`read_file`，不能获得写工具、命令工具或委派工具；
3. 最终生成 `exploration-report.json`；
4. 报告包含 summary、evidence、root cause、next steps 和 risks；
5. 每条 evidence 都是存在的相对路径与真实行号；
6. Trace 首尾包含 `subagent_started` 与 `subagent_completed/failed`；
7. `.env` 等受保护路径不能作为证据，Trace 和报告不能包含 API Key；
8. 达到步骤或 Token 预算时应明确以 `budget_exhausted` 停止，不能伪装成功。

查看 child 时间线：

```powershell
.\start.cmd replay <child_run_id>
```

全部满足时 M5.1 PASS。出现写操作、越界证据、虚假行号或无独立 Trace 时 FAIL。

## 10. M5.2：主 Agent 委派与父子协作

### 10.1 真实父子闭环

```powershell
.\start.cmd demo
```

如果简单任务没有触发委派，可在 `webdemo` 中明确要求：

```text
先委派 Explore Subagent 定位实现、测试和边界风险；父 Agent 复核证据后修复问题，运行测试并检查 Diff。
```

### 10.2 必须看到的证据

1. parent 产生 `subagent_delegated`，随后出现独立 Child Run ID；
2. child 使用独立 Prompt、上下文、Provider、步骤/Token 预算和 Trace；
3. child 只返回经过校验的结构化报告，不把内部完整消息灌入 parent；
4. parent 在 `apply_patch` 前重新读取至少一个 child 引用的源码文件；
5. 未复核证据就 Patch 时，工具层返回 `subagent_evidence_unverified`；
6. parent 最终完成 Patch、测试、Diff 与 `finish_task`；
7. child 失败时 parent 能使用自己的 search/read 降级继续，而不是整个任务崩溃；
8. 每个 parent 最多委派两次，第三次应被 `delegation_limit` 拒绝；
