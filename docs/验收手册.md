# MiniCode 分阶段验收手册

本文把“功能完成”拆成两层：

- **自动验收**：运行测试或评测脚本，有明确退出码和报告；
- **手动验收**：你亲自在终端观察行为，确认体验和结果符合预期。

任何阶段只有同时满足硬性标准，才算通过。模型回答措辞不要求固定，但工具权限、事件、测试和文件产物必须可验证。

## 0. API Key 放在哪里

DeepSeek 官方当前 Flash 模型名为 `deepseek-v4-flash`，Base URL 为 `https://api.deepseek.com`。

在项目目录 `D:\000Study\agentProgram` 中执行：

```powershell
Copy-Item .env.example .env
notepad .env
```

把第一行改为你的真实 Key：

```dotenv
DEEPSEEK_API_KEY=sk-xxxxxxxxxxxxxxxx
MINICODE_BASE_URL=https://api.deepseek.com
MINICODE_MODEL=deepseek-v4-flash
```

安全要求：

- 不要把 Key 发到聊天里；
- 不要修改 `.env.example` 填入真实 Key；
- `.env` 已被 `.gitignore` 排除；
- M0 的 `read_file/search_code/list_files` 均不能访问 `.env`；
- Trace 中不会主动记录 Key。

## 2. M0：只读仓库分析 Agent

Windows 日常验收可优先使用简易脚本：

```powershell
.\start.cmd test
.\start.cmd
.\start.cmd eval
```

手册保留底层完整命令，便于定位脚本和 Agent 本身的问题。

### M0 范围

M0 只验证最小 Agent 闭环：

```text
自然语言问题
→ DeepSeek 决定调用工具
→ 目录/搜索/文件读取
→ 工具结果返回模型
→ 流式输出带代码引用的回答
→ 保存 Trace
```

M0 有运行内上下文和完整事件记录，但尚无跨会话记忆、checkpoint/resume 或上下文压缩。不要用 M1/M2 的标准验收 M0。

### 2.1 自动验收：离线测试

不需要 API Key：

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

通过标准：

- 所有测试显示 `ok`；
- 最后显示 `OK`；
- 测试数量不少于 10；
- 退出码为 0；
- 测试期间不产生 API 费用。

覆盖功能：路径越界、`.env` 保护、目录列表、代码搜索、按行读取、工具白名单、流式工具 chunk 拼接、事件持久化、默认模型配置。

### 2.2 手动验收 A：配置错误

临时指定不存在的配置：

```powershell
.\.venv\Scripts\python.exe run_mini_code.py ask "入口在哪里？" --workspace . --env-file missing.env
```

通过标准：

- 显示缺少 `DEEPSEEK_API_KEY`；
- 不出现 Python traceback；
- 退出码非 0；
- 不创建一个伪成功任务。

PowerShell 可用 `$LASTEXITCODE` 查看退出码。

### 2.3 手动验收 B：真实只读分析

确保已填写 `.env`，执行：

```powershell
.\.venv\Scripts\python.exe run_mini_code.py ask "M0 向模型提供了哪些只读工具？分别有什么作用？请引用代码行" --workspace .
```

通过标准：

- 终端依次出现 `[启动]`、`[仓库]`、`[模型]`；
- 至少出现一次 `[工具]` 和 `[结果]`；
- 文本是逐步流式出现，而不是等待全部结束后一次打印；
- 回答包含 `list_files`、`search_code`、`read_file`；
- 回答引用 `src/mini_code/tools/readonly.py:<行号>`；
- 最后出现 `[完成]`、Run ID 和 Trace 路径；
- 退出码为 0；
- `git diff` 不出现 Agent 修改的源代码。

### 2.4 手动验收 C：轨迹记录

复制上一步输出的 Run ID：

```powershell
.\.venv\Scripts\python.exe run_mini_code.py trace <run_id> --workspace .
```

通过标准：

- 能看到 `run_started`；
- 能看到 `repository_mapped`；
- 能看到 `tool_started` 和 `tool_completed`；
- 最后是 `run_completed`；
- `.mini-code/runs/<run_id>/events.jsonl` 存在；
- 文件每行都是合法 JSON；
- 文件中搜索不到你的真实 API Key。

检查 Key 是否泄漏时，不要把 Key 直接写进命令历史；可人工打开 Trace 搜索 Key 的一小段非敏感前缀。

### 2.5 手动验收 D：安全边界

执行自动安全用例：

```powershell
.\.venv\Scripts\python.exe -m unittest tests.test_tools.ReadOnlyToolTests.test_tools_reject_path_escape -v
.\.venv\Scripts\python.exe -m unittest tests.test_tools.ReadOnlyToolTests.test_tools_reject_env_file_containing_api_key -v
```

通过标准：两个测试均为 `ok`。这比询问模型“你会不会读取 Key”更可靠，因为拦截发生在工具层。

### 2.6 手动验收 E：5 题真实模型评测

该步骤会调用 DeepSeek 并产生少量费用：

```powershell
.\.venv\Scripts\python.exe run_mini_code.py eval-m0 --workspace .
```

通过标准：

- 5 个任务都完成，没有 provider/tool runtime error；
- 每个任务至少调用一次工具；
- 至少 4/5 自动评分为 PASS；
- 唯一失败若来自措辞未命中，人工查看答案确认是否真的错误；
- 报告写入 `.mini-code/evals/<suite_id>/report.json`；
- 报告记录模型名，但不包含 API Key。

为什么不是强制 5/5：M0 grader 是低成本字符串规则，模型可能给出正确同义表达却未命中。若任务本身答错、没有引用或没有工具证据，则不能人工豁免。

### 2.7 M0 总通过条件

M0 只有同时满足以下条件才通过：

- 离线自动测试全部通过；
- 真实分析可以流式调用工具并引用代码；
- Trace 完整且不包含 Key；
- 路径越界和 `.env` 访问在工具层被拒绝；
- 真实评测至少 4/5，且没有运行时错误；
- Agent 没有修改被分析仓库。

## 3. M1：可修改、可验证 Coding Agent

### 自动验收

```powershell
.\start.cmd test
```

通过标准：显示 `Ran 19 tests` 和 `OK`。自动用例覆盖：

- unified diff 正常修改与错误 context 拒绝；
- 无计划不能 Patch，`.env` 和越界路径不能 Patch；
- Shell、`python -c` 等非白名单命令被拒绝；
- 最新 Patch 会使旧测试证据失效；
- 计划未完成、测试未通过或未查看 Diff 时，`finish_task` 拒绝完成；
- 端到端执行“错误 Patch → 测试失败 → 再次 Patch → 测试通过 → Diff → 完成协议”；
- 三个 M1 版本化样例在修复前确实存在失败测试。

### 手动 Demo 验收

API Key 仍只填写在项目根目录 `.env`。运行：

```powershell
.\start.cmd demo
```

该命令会先复制一个新的临时样例到 `.mini-code/demos/m1-<id>/`，因此不会修改原始 Demo 模板。

通过标准：

1. 输出包含仓库读取、计划、测试、Patch 和 Diff 工具事件；
2. 修改前的除零测试失败，修改后的测试通过；
3. 出现 `[验证] 测试通过` 和 `[协议] 完成协议已通过`；
4. 最终回答列出 `calculator.py`、实际测试命令和剩余风险；
5. 打开输出所示 Demo 目录，`calculator.py` 已处理除数为零；
6. 在该目录运行以下命令仍为 2 个测试全部通过：

```powershell
D:\000Study\agentProgram\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

如果 Agent 第一次 Patch 后测试仍失败，但能根据错误再次 Patch 并通过，这是预期且更有演示价值；不能把中间失败误判为整次任务失败。

### 三题真实模型评测

```powershell
.\start.cmd eval1
```

评测依次复制并修复除零、区间 clamp 和标签规范化三个单文件 Bug。grader 测试位于 Agent 工作区之外，修改公开测试不能绕过评分。

正式通过标准：

- 最终显示 `M1 result: 3/3 passed`；
- 报告 `.mini-code/evals/m1-*/report.json` 中三题均为 `passed: true`；
- 每题 `agent_status` 为 `completed`、`tests_passed` 为 `true`、`changed_files` 非空；
- Trace 包含 plan、patch、verification 和 completion 事件；
- 无 Provider、Patch、命令策略或测试运行时错误。

### M1 功能判定

以下全部满足，M1 才能从“待人工验收”改为“已通过”：

- Agent 先读代码和测试，再建立计划；
- 只通过 unified diff 修改文件；
- 修改范围不越过 workspace；
- 主动运行修改后的测试；
- 首次测试失败时能根据错误继续修改；
- 最终公开测试和隐藏测试通过；
- 输出最终 Diff、验证命令和剩余风险；
- 没有验证证据时不能标记 completed；
- 三题 M1 评测达到 3/3。

安全边界：M1 会过滤测试子进程中的常见密钥变量，并限制模型选择的命令，但还不是操作系统沙箱。仓库测试代码仍以你的当前 Windows 用户权限运行；只对可信本地仓库使用 M1，容器隔离属于后续安全阶段。

## 4. M2：上下文、压缩与任务恢复

### 自动验收

```powershell
.\start.cmd test
```

通过标准：显示 `Ran 22 tests` 和 `OK`。M2 专项测试必须证明：

- SQLite 最新状态和 JSON checkpoint 同时存在；
- `.mini-code` 内部运行数据不会触发工作区冲突；
- checkpoint 后修改源码会触发 `WorkspaceConflictError`；
- 大工具输出生成 artifact，模型消息明显小于原结果；
- 压缩后仍保留 durable state 中的计划和修改文件；
- Provider 在 Patch 后失败时，resume 从下一步继续且不重复 Patch；
- 恢复后的测试、Diff 和完成协议可以正常通过。

### 手动可恢复 Demo

运行：

```powershell
.\start.cmd demo2
```

该命令会：

1. 创建一次性 Demo workspace；
2. 临时降低上下文和 artifact 阈值；
3. 使用真实 DeepSeek 执行 Coding Agent；
4. 在总步骤预算 6 处主动暂停并保存 checkpoint；
5. 命令结束后恢复原环境变量。

记下输出中的 `Disposable demo workspace` 和 `Run ID`。查询状态：

```powershell
.\start.cmd status <run_id> "<Demo workspace>"
```

应显示非 completed 状态、已执行步骤、checkpoint 编号、当前计划和已修改文件。然后恢复：

```powershell
.\start.cmd resume <run_id> "<Demo workspace>"
```

恢复成功后再次执行 status，应显示 `Status: completed`。查看 Trace：

```powershell
.\start.cmd trace <run_id> "<Demo workspace>"
```

通过标准：

- Trace 出现 `context_compacted`；
- 大型测试日志落入 artifact，模型上下文只保留摘要和引用；
- 压缩后仍保留任务目标、当前计划、最新 Diff 和未解决错误；
- 进程中断前存在 checkpoint；
- `resume <run_id>` 不从头探索仓库；
- 恢复前校验工作区 Diff；
- 用户修改工作区后，Agent 能发现冲突并暂停；
- 恢复任务最终通过测试。

运行产物位于 Demo workspace：

```text
.mini-code/state.db
.mini-code/runs/<run_id>/events.jsonl
.mini-code/runs/<run_id>/checkpoints/*.json
.mini-code/runs/<run_id>/artifacts/*.txt
```

冲突检测已由自动测试覆盖。若要手动验证，可新建第二个 `demo2`，暂停后修改其源码，再执行 resume；应显示 `Resume conflict` 且不产生新的 Patch。不要在准备继续完成的唯一 Demo 上做这个实验。

## 5. M3：安全、评测与可投递版本

已实现 Replay、15 个策略探针、模型故障注入、20 个版本化任务和指标报告。

### 自动验收（不需要 API Key）

```powershell
.\start.cmd test
.\start.cmd security
```

成功标准：第一条显示 `Ran 27 tests` 和 `OK`；第二条显示 `15/15 blocked`，并在 `.mini-code/security/` 生成 JSON 报告。15/15 仅代表当前探针全部被策略层阻断，不代表拥有 OS 沙箱。

### 手动验收（需要 API Key）

先在根目录 `.env` 填写 `DEEPSEEK_API_KEY`，然后运行一个真实任务并记下 Run ID：

```powershell
.\start.cmd run "在一个可信测试仓库中修复 Bug，运行测试并查看 Diff"
.\start.cmd replay <run_id> "<该任务的 workspace>"
```

Replay 成功标准：按序显示计划、工具、Patch、测试和结束事件；Summary 的状态、步骤、工具次数和改动文件与原运行一致；模型返回 usage 时 Token 不为 `unavailable`。

故障恢复使用底层命令在可信测试仓库执行：

```powershell
.\.venv\Scripts\python.exe run_mini_code.py run `
  "修复 Bug，运行测试并查看 Diff" `
  --workspace D:\path\to\test-repo --env-file .env --fail-model-call 2
.\start.cmd status <run_id> "D:\path\to\test-repo"
.\start.cmd resume <run_id> "D:\path\to\test-repo"
```

成功标准：首次运行明确报告 injected failure 并保存 checkpoint；`status` 可见中断状态；`resume` 不重复已经完成的 Patch，最终通过测试与完成协议。

真实评测建议先试 1 题，再运行 20 题；后者会消耗明显更多 Token：

```powershell
.\start.cmd eval3 1
.\start.cmd eval3 20
```

成功标准：生成 `.mini-code/evals/m3-*/report.json`；报告总题数与参数一致，包含成功率、回归率、无关修改率、平均步骤、P50/P95、Token 覆盖和成本字段。成本可为 `null`，除非 `.env` 配置两个价格快照且 API 返回 usage。任务未全部通过不等于程序崩溃，应结合每题 Trace 记录为模型失败案例。

通过标准：

- `replay <run_id>` 可重放计划、工具、Patch、测试和上下文压缩事件；
- 提示注入、路径穿越、命令注入测试全部在策略层被拦截；
- 至少 20 个版本化任务可一键运行；
- 报告包含成功率、回归率、无关修改率、平均步骤、Token、成本和 P95；
- 新环境按 README 5 分钟内运行 Demo；
- 正常任务、失败恢复、安全拦截三个演示均成功；
- README 如实列出失败案例，不宣称“媲美 Claude Code”或“绝对安全”。
